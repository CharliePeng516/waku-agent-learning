线上到底发生了什么

你已经很熟悉一次 REST 调用的样子：method、URL、headers、一个 JSON body、一个 JSON 响应。 LLM API 调用本质上还是这个样子，只是多套了四个不太一样的字段——系统提示词、 消息历史、工具（tools）、以及用量统计（token usage）。 这节课的目标就是先把这个结构看清楚、看一次，这样后面每一课（结构化输出、工具调用、agent）读起来 都只是这个结构上的变体，而不是新的魔法。

推荐首选资料

建议课前或课后通读一遍 Anthropic 官方的 Messages API 文档。这节课里的一切最终都能追溯到那份文档——它是说明书，这节课是导览。

1. 请求（Request）

每一次调用 LLM，至少要发送：用哪个模型、遵循什么常驻指令、以及到目前为止的完整对话。 用 Anthropic 的格式写出来是这样：

client.messages.create(
    model="claude-sonnet-5",
    system="You are a terse, helpful assistant.",
    messages=[
        {"role": "user", "content": "What's 12% of 850?"}
    ],
    max_tokens=1024,
)

有两点值得注意，对于习惯了"有状态"后端的人来说尤其容易忽略：

  • 这个 API 是无状态的。 服务端不存在"会话"这种东西。如果这是对话的第 5 轮， messages 里就要包含全部 5 轮——每一次调用都要把完整历史重新发一遍。这也是为什么 waku-agent 会在内存里维护一个 messages 列表并逐轮修改它，而不是指望 provider 帮你"记住"什么。
  • max_tokens 限制的是回复长度，不是整次交互的长度。 它只是一个"输出预算"。设错了不会报错——你只会得到一段被从半句话中间截断的回复， 并且 stop_reason 会是 "max_tokens"。

2. 响应（Response）

回复以一组内容块（content blocks）的形式返回，而不是单个字符串——因为同一条助手回复 可能既包含文本，也包含一个调用工具的请求：

Message(
    content=[ContentBlock(type="text", text="12% of 850 is 102.")],
    stop_reason="end_turn",
    usage=Usage(input_tokens=24, output_tokens=11),
)

stop_reason 就是你代码里要做分支判断的字段。"end_turn" 表示模型已经把话对人说完了。第 4 课会引入 "tool_use"，意思正好相反：模型还没说完， 它是在请求你的代码去执行点什么，然后再把结果带回来。

概念

usage 不是可有可无的遥测数据——它就是你这一次调用的账单，也是生产环境里你真正会 设告警阈值去盯的数字。现在就习惯读它；第 10 课会专门回来讲成本预算。

3. 到真实代码里读一遍：waku/loop/agent.py

打开 waku-agent 仓库里的 waku/loop/agent.py，找到 run_loop 函数。大约第 79–86 行是一次裸露、未加任何包装的 client.messages.create(...) 调用——和上面完全一样的结构，只是换成了真实变量。 再看第 91 行：

messages.append({"role": "assistant", "content": response.content})
为什么要这么写

这一行代码就是解决"无状态"问题的关键。助手的回复被重新追加回 messages，这样循环下一次调用时才能把它当作历史看到。如果去掉这一行， 模型在第二轮迭代时就会"忘记"自己上一轮说过什么——因为从机制上讲，根本没有什么"服务端记忆"可以丢失。

现在再看文件开头（第 1–16 行）的注释块。它用七行伪代码把整个循环先写了一遍，然后才是真正的代码。 读一下这七行，再对照真正的函数看它们贴合得有多紧。伪代码到生产代码之间的这段"落差"被刻意做得很小， 而缩小这段落差，基本上就是这整个课程在教的东西。

4. 不存在"通用"的线上格式

打开 waku/loop/models.py，找到 OpenAICompatClient 类 （大约第 296 行）。它唯一的工作，就是把 OpenAI 的 chat-completions 格式翻译成上面那种 Anthropic 格式，这样代码库的其余部分就永远不用关心自己到底在跟哪个 provider 说话。

浏览一下 _to_openai 和 _create。现在不需要看懂每一行—— 只要自己确认一下这个翻译确实做了实事：字段名不一样（stop_reason 对 finish_reason），而且 OpenAI 那边工具调用的参数是以 JSON 字符串 形式送过来的， 需要先解析出来，才能变成 Anthropic 那种已经是解析好的字典的 input。

完整对照表见： reference/api-request-response-cheatsheet.zh.html。

5. 练习

练习 — 自己动手做，做完再拿回来一起 review

写一个独立的 Python 脚本，放在 waku 包之外（不要 import 任何 waku.*）——只用原生的 anthropic SDK。用这个仓库 .env 里已有的 key。脚本要做到：

  1. 发送一条 user 消息，问一个你自己知道答案的事实性问题。
  2. 打印出回复文本。
  3. 打印出 stop_reason，以及 usage 里的两个 token 数量。

然后，不查任何资料，自己扩展一下：加一个 system 提示词，改变助手的语气或输出格式 （比如"只用一句话回答，不要标点"），重新跑一遍，确认输出确实变了。整个练习就这些——没有工具、 没有循环、没有框架。

卡在 SDK 用法上，不是卡在概念上？（提示）

anthropic 这个包已经是本仓库的依赖之一（见 uv.lock）。 client 的构造方式和 messages.create 的具体关键字参数，在 waku/loop/models.py 和 waku/loop/agent.py 里都能看到—— 允许照抄这两处的语法，这个练习的重点是理解请求/响应的结构，不是要你凭空记住 SDK 方法名。
