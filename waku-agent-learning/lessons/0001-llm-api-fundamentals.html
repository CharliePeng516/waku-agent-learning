What actually happens on the wire

You already know the shape of a REST call: method, URL, headers, a JSON body, a JSON response. An LLM API call is that same shape with four unusual fields — system prompt, message history, tools, and token usage — layered on top. This lesson is about seeing that shape clearly, once, so every later module (structured output, tool calling, agents) reads as a variation on it instead of new magic.

Primary source

Read (or skim) Anthropic's own Messages API reference before or after this lesson. Everything here traces back to it — this lesson is the tour, that's the manual.

1. The request

Every call to an LLM sends, at minimum: which model, what standing instructions to follow, and the conversation so far. In Anthropic's shape:

client.messages.create(
    model="claude-sonnet-5",
    system="You are a terse, helpful assistant.",
    messages=[
        {"role": "user", "content": "What's 12% of 850?"}
    ],
    max_tokens=1024,
)

Two things to notice, both easy to miss coming from a typical stateful backend:

  • The API is stateless. There's no session on the server. If this is turn 5 of a conversation, messages contains all 5 turns — you resend the entire history, every single call. That's why waku-agent keeps a messages list in memory and mutates it turn by turn rather than trusting the provider to "remember."
  • max_tokens caps the reply, not the whole exchange. It's an output-only budget. Get it wrong and you don't get an error — you get a reply cut off mid-sentence, reported via stop_reason: "max_tokens".

2. The response

The reply comes back as a list of content blocks, not a single string — because a single assistant turn can contain text and a request to call a tool in the same response:

Message(
    content=[ContentBlock(type="text", text="12% of 850 is 102.")],
    stop_reason="end_turn",
    usage=Usage(input_tokens=24, output_tokens=11),
)

stop_reason is the field your code branches on. "end_turn" means the model is done talking to the human. Module 4 introduces "tool_use", which means the opposite: the model isn't finished, it's asking your code to go run something and come back.

Concept

usage is not incidental telemetry — it's your bill, per call, and the number you'd alert on in production if it spiked. Get comfortable reading it now; module 10 comes back to it for cost budgeting.

3. Read it in the wild: waku/loop/agent.py

Open waku/loop/agent.py in the waku-agent repo and find run_loop. Around line 79–86 is a bare, undecorated client.messages.create(...) call — the exact shape above, just with real variables. Then look at line 91:

messages.append({"role": "assistant", "content": response.content})
Why it's written this way

That one line is the statelessness fix. The assistant's response gets appended back onto messages so the next call in the loop sees it as history. Skip that line and the model would "forget" its own previous turn on iteration 2 — because, mechanically, there is nothing to forget from. There's no server-side memory to lose.

Now find the comment block at the top of the file (lines 1–16). It writes the entire loop out as seven lines of pseudocode before any real code appears. Read those seven lines, then look at how closely the real function follows them. That gap — pseudocode to production code — is small on purpose, and closing it is most of what this whole curriculum is about.

4. There is no universal wire format

Open waku/loop/models.py and find the class OpenAICompatClient (around line 296). Its entire job is translating OpenAI's chat-completions shape into the Anthropic shape above, so the rest of the codebase never has to know which provider it's talking to.

Skim _to_openai and _create. You don't need to understand every line yet — just confirm for yourself that the translation is doing real work: field names differ (stop_reason vs finish_reason), and tool-call arguments arrive as a JSON string on OpenAI's side that has to be parsed before it looks like Anthropic's already-parsed input dict.

5. Exercise

Exercise — do this yourself, then bring it back for review

Write a standalone Python script, outside the waku package (no imports from waku.*) — just the raw anthropic SDK. Use the key already in this repo's .env. The script should:

  1. Send a single user message asking a factual question you know the answer to.
  2. Print the reply text.
  3. Print stop_reason and both token counts from usage.

Then, without looking anything up, extend it: add a system prompt that changes the assistant's tone or format (e.g. "answer in exactly one sentence, no punctuation"), rerun, and confirm the output actually changed. That's the whole exercise — no tools, no loop, no framework.

Stuck on SDK setup, not the concept? (hint)

The anthropic package is already a dependency of this repo (uv.lock). The client constructor and the exact keyword arguments for messages.create are both visible in waku/loop/models.py and waku/loop/agent.py — you're allowed to look at those for syntax, the point of this exercise is understanding the request/response shape, not memorizing SDK method names.
